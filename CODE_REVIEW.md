3 questions for the judges to ask this team in their Defence, aimed at the weakest spots you found:
1. Ingestion concurrency and SQLite write locking: Ingestion relies on SQLite WAL mode and a busy timeout (app/db/database.py:43-44) where concurrent workers contend on the unique constraint. While this eliminates external infrastructure and passes concurrent test scenarios, SQLite serializes writes. How would this architecture scale if the Indian AI API startup experienced thousands of concurrent event ingestion requests per second across distributed gateway workers?
2. Multi-upgrade interaction within a single cycle: As noted in README.md:270-272 and app/services/subscription.py:85-189, each plan upgrade immediately creates a one-off proration settlement invoice and updates subscription line items. If a customer upgrades on Day 10 and changes plan again on Day 20 within the same calendar month, how do the opposing credits interact with the final cycle invoice, and how would tax (GST) or cumulative usage tiers reconcile across multiple overlapping plan intervals?
3. Spike baseline evaluation under bursty workloads: The spike detector computes the baseline as integer tokens per hour across the 167 hours preceding the current hour (app/services/spike_detector.py:47). For an AI startup whose API clients send batch embedding jobs once a week at midnight, the 7-day hourly average will be low, potentially triggering false-positive spike alerts during regular weekly batch jobs. How could the spike anomaly detector distinguish between legitimate scheduled batch bursts and genuine runaway prompt loops?
